> 2026-09-24 设计 · 2026-09-29 实作更新（构建段已落地，见"第七步"）· 前置状态：Jenkins（ns jenkins，devops-m1）/ GitLab CE 17.9.1（ns gitlab，devops-m1）/ Harbor 2.15.2（ns harbor，devops-w1）已就绪，统一入口 ingress-nginx NodePort 32037（EIP 123.58.219.112）。
> 前置：本机及所有操作机 hosts 已加 `123.58.219.112 jenkins.devops.local gitlab.devops.local harbor.devops.local`
> 凭据：GitLab root / `Dev0ps#2026` · Harbor admin / `Harbor12345`
>
> 各步状态：第一步 ✅ · 第二步 ✅ · 第三步 ✅（prod-pull 未建）· 第四步 ⬜（部署段再议）· 第五步 ✅（实作为 BuildKit 路线）· 第六步 构建段 ✅ / 部署段 ⬜ · **第七步（BuildKit 实作）= 当前真实路线 ✅**

```
git push → GitLab webhook → Jenkins 流水线
                                  ├─ kaniko pod 构建 + push 镜像 → Harbor (demo/demo-app:TAG)
                                  └─ kubectl apply 到 prod 集群 ns demo → Gateway API/NodePort 访问
```

关键前提（都是踩过的坑，见《环境搭建.md》）：

1. **GitLab API 无密码 Basic Auth**（16.0+ 移除），所有 API/CI 集成必须用 PAT
2. **Harbor 无 TLS**：客户端 containerd/docker 必须配 insecure registry，且必须用域名（externalURL 钉死 `harbor.devops.local:32037`）
3. prod 节点不在 devops 集群，**必须显式配 hosts + containerd http 拉取**才能用 Harbor 镜像

界面：项目 demo → Robot Accounts → Add Robot。实际用系统级 API 建（2026-09-29，Harbor 2.15.2）：

| Robot | 权限 | 用途 | 状态 |

> - 用户名格式是 **`robot$项目名+robot名`**（如 `robot$demo+jenkins-push`），不是旧文档的 `demo+jenkins-push`；认证必须用完整名

> - 老字段组合 `project_id` + `access` 报 400 "bad request empty permission"——用上面 `permissions` 结构
> - secret 只在创建响应里出现一次
> - `GET /api/v2.0/robots` 列表返回空（2.15 quirk），但 `GET /api/v2.0/robots/1` 能查到、认证也正常——按 id 查单个为准

### 3. prod 节点拉取 Harbor 镜像（三节点都要）

无 TLS + 域名不在公网 DNS，containerd 必须显式指路。每个 prod 节点：

```bash
# hosts（prod 节点访问 devops 内网走 10.7.6.245）
echo '10.7.6.245 harbor.devops.local' >> /etc/hosts

# containerd 明文 http 拉取 + 跳过端口 32037 的证书校验
mkdir -p /etc/containerd/certs.d/harbor.devops.local:32037
cat > /etc/containerd/certs.d/harbor.devops.local:32037/hosts.toml <<'EOF'
server = "https://harbor.devops.local:32037"

[host."https://harbor.devops.local:32037"]
  capabilities = ["pull", "resolve"]
  skip_verify = true
  override_path = false
EOF

systemctl restart containerd
```

验证（节点上）：

```bash
crictl pull harbor.devops.local:32037/demo/demo-app:v1   # 推送第一个镜像后测
```

> 坑：hosts.toml 的 server 也可写 http://，但配合 skip_verify 用 https 表达式更稳。若 config.toml 没开 `config_path`，需要在 /etc/containerd/config.toml 的 [plugins."io.containerd.grpc.v1.cri".registry] 下加 `config_path = "/etc/containerd/certs.d"` 再重启。
> prod ns demo 里业务 Pod 拉私有镜像还需 imagePullSecrets 或项目 robot 的 dockerconfigjson Secret：

```bash

  --docker-server=harbor.devops.local:32037 \
  --docker-username='demo+prod-pull' --docker-password='<prod-pull secret>'
# deploy.yaml spec.template.spec 加 imagePullSecrets: [{name: harbor-pull}]
```

### 3. Agent / 构建方式（Cloud 只需一套，且无需手动配）

**Cloud（Manage Jenkins → Clouds）不需要手动配置，也只需要一套**：

- Cloud Kubernetes Configuration 只决定"构建 agent（jnlp pod）在哪个集群起"，与"部署目标集群"无关。
- chart 安装时已自动建好唯一需要的 cloud：name `kubernetes`，serverUrl `https://kubernetes.default`（devops 集群内 SA 免凭据），ns `jenkins`，默认模板 label `jenkins-jenkins-agent`。
- prod 集群**不建 cloud**：deploy 阶段是在 devops 的 agent pod 里用 `prod-kubeconfig` 凭据跑 kubectl 远程操作 prod apiserver（10.7.94.38:6443，devops pod 实测可达）。
- 仅当要让构建 agent 以 pod 跑在 prod 时才加第二套 cloud（本流水线不需要）：Add a new cloud → Kubernetes，URL `https://10.7.94.38:6443`，Credentials 填 prod SA token（Secret text，需 prod 里给 SA 授 pods create），Jenkins URL 必须写 prod 可达的地址（如 EIP `http://123.58.219.112:32037`——默认的 `http://jenkins.jenkins.svc.cluster.local:8080` 在 prod 解析不了，agent 连不回控制器），自签证书勾 Disable https certificate check。

构建方式两种选一：

**方式 A（简单）**：Jenkinsfile 直接 `podTemplate`，流水线里起 kaniko pod 构建。无需预配 agent 池。

**方式 B（正式）**：Manage Jenkins → Nodes → Pod Templates 预定义 kaniko/maven 模板。

推荐 A，模板写在 Jenkinsfile 里随仓库走。

### 4. Jenkinsfile（完整版，放仓库根目录）

> ⚠️ 本小节的 kaniko 路线**未实施**（kaniko 已 EOL：最后版本 v1.23.x，2025 年起停止维护）。实际落地为 **BuildKit 常驻构建农场**，见"第七步"。本节保留作选型对照；其中 `harbor-push-config` Secret 的创建方式（key 必须叫 `config.json`）BuildKit 路线原样复用（已建）。

```groovy
def tag = "b${env.BUILD_NUMBER}-${sh(script: 'git rev-parse --short HEAD', returnStdout: true).trim()}"

pipeline {
  agent any
  options { timestamps(); disableConcurrentBuilds() }
  environment {
    HARBOR = 'harbor.devops.local:32037'
    PROJECT = 'demo'
    APP = 'demo-app'
  }
  stages {
    stage('Build & Push (kaniko)') {
      steps {
        script {
          // Secret file 凭据必须挂进 pod，kaniko 才能认证
          podTemplate(name: 'kaniko', label: 'kaniko',
              containers: [
                containerTemplate(name: 'kaniko', image: 'gcr.io/kaniko-project/executor:debug',
                  command: ['sleep'], args: ['9999999'],
                  ttyEnabled: true)
              ],
              volumes: [
                secretVolume(secretName: 'harbor-push-config', mountPath: '/kaniko/.docker')
              ]) {
            node('kaniko') {
              container('kaniko') {
                sh """
                  /kaniko/executor \
                    --context=git://gitlab.devops.local:32037/root/demo-app.git#refs/heads/main \
                    --destination=${HARBOR}/${PROJECT}/${APP}:${tag} \
                    --insecure --skip-tls-verify --cache=false
                """
              }
            }
          }
        }
      }
    }
    stage('Deploy to prod') {
      steps {
        withCredentials([file(credentialsId: 'prod-kubeconfig', variable: 'KCFG')]) {
          sh '''
            sed "s|BUILD_PLACEHOLDER|'${tag}'|" k8s/deploy.yaml > deploy-apply.yaml
            KUBECONFIG=$KCFG kubectl apply -f deploy-apply.yaml
            KUBECONFIG=$KCFG kubectl -n demo set image deployment/demo-app demo-app=${HARBOR}/${PROJECT}/${APP}:${tag}
            KUBECONFIG=$KCFG kubectl -n demo rollout status deployment/demo-app --timeout=180s
          '''
        }
      }
    }
  }
}
```

kaniko 认证 Secret（jenkins ns 里建一次，**key 必须叫 `config.json`**）：

> 坑：不能用 `create secret docker-registry`——它生成的 key 是 `.dockerconfigjson`，而 kubernetes 插件的 secretVolume 不支持 items 重命名，挂出来是 `/kaniko/.docker/.dockerconfigjson`，kaniko 只认 `config.json`，照样 unauthorized。

```bash
AUTH=$(printf 'robot$demo+jenkins-push:<robot secret>' | base64)
cat > /tmp/config.json <<EOF
{"auths":{"harbor.devops.local:32037":{"username":"robot$demo+jenkins-push","password":"<robot secret>","auth":"$AUTH"}}}
EOF
kubectl --context devops -n jenkins create secret generic harbor-push-config \
  --from-file=config.json=/tmp/config.json
rm -f /tmp/config.json
```

> 已建实况：secret `harbor-push-config`（ns jenkins，generic，key=`config.json`，用户名 `robot$demo+jenkins-push`，secret `yacDNbefbXGp0MjEnD1jCAWjmWMESAEt`）。BuildKit 路线会把它挂两份：buildkitd daemon + agent pod 的 buildctl 容器（见第七步，缺 agent 侧那份就是 401）。

> 坑：kaniko `--insecure` 必须加（Harbor 无 TLS）；`--destination` 必须带 `:32037` 端口；Jenkinsfile 里 sed 替换镜像 tag 时 `deploy.yaml` 的 image 字段要用 `BUILD_PLACEHOLDER` 占位。
> 坑：kaniko 需要仓库内容，`--context=git://` 会再 clone 一次。更简单的做法是流水线先 checkout 再用 `--context=$WORKSPACE`，但 pod 间共享 workspace 要 PVC/共享卷，git context 免共享卷。

**构建方案选型——为什么用 kaniko（而不是 docker.sock / DinD）**：

经典问题是"jnlp 容器只有 docker cli 没有 daemon，习惯做法是挂宿主机 /var/run/docker.sock"。但本集群运行时是 containerd，节点上没有 docker daemon，sock 这条路天然走不通。各方案对比：

| 方案 | 原理 | privileged | 评价 |
|---|---|---|---|
| 挂宿主 docker.sock | 复用节点 daemon | 不需要（但等同节点 root） | containerd 集群无 sock 可挂；即使有也是最大安全隐患，弃 |
| DinD（Pod/sidecar 跑 dockerd） | 独立 daemon，`DOCKER_HOST=tcp://localhost:2375` | **必须要** | 兼容 docker CLI 老流水线；特权容器 + 镜像层不共享 + 嵌套 overlayfs 慢，仅救急 |
| **kaniko（本方案）** | 用户态逐条执行 Dockerfile，直 push 仓库 | 不需要 | 无 daemon 无特权无 sock，K8s 原生；`--insecure` 兼容无 TLS Harbor，认证走挂载的 dockerconfigjson |
| BuildKit（buildkitd + buildctl/buildx） | 构建器独立部署，有 rootless 模式 | rootless 免特权 | 最先进：多阶段并行最快、`RUN --mount=type=cache/secrets`、多平台构建；`buildx create --driver kubernetes` 按需起 buildkitd |
| nerdctl / kit | containerd 原生构建 | 视模式 | nerdctl 底层仍是 buildkitd；kit（CNCF 沙箱）专为无特权容器内构建设计，生态尚早 |

本流水线全程不碰 docker CLI：podTemplate 起 kaniko pod → 用户态执行 Dockerfile → 直 push Harbor。后续：镜像变大后开远程缓存 `--cache=true --cache-repo=${HARBOR}/demo/cache`（当前 `--cache=false` 对 busybox 无所谓）；需要并行构建/构建期 secret/多平台时再上 BuildKit。

## 第七步：BuildKit 构建农场实作（2026-09-29 已落地，**当前真实路线**）

> kaniko 已 EOL，本环境实际落地 BuildKit：**常驻 rootless buildkitd（构建农场）+ agent pod 里的 buildctl 客户端**。
> 产物：`buildkitd.yaml`（本目录）。构建段 4 连绿：`demo/demo-app:b1..b4`，其中 b4 命中 registry 缓存（日志 `#9 CACHED`）。

### 1. 架构

```
Jenkins job demo-app（Pipeline from SCM · lightweight checkout · http+PAT 拉 GitLab）
  └─ agent pod（cloud 模版 buildkit，ns jenkins，label buildkit）
       ├─ jnlp：回连 controller（chart 预置）
       └─ buildctl 容器（moby/buildkit:v0.33.0-rootless · sleep 9999999 + tty）
            ├─ ~/.docker/config.json ← Secret harbor-push-config  ← 认证源（关键！见 §3）
            └─ buildctl --addr tcp://buildkitd.jenkins.svc.cluster.local:1234 build …
                 └─ buildkitd Deployment（rootless · devops-w1 · PVC buildkit-cache 20Gi 本地缓存）
                      ├─ 拉基础镜像：demo/busybox:1.36（skopeo 转存进 Harbor，绕开 docker.io 香港超时）
                      ├─ 推产物：demo/demo-app:bN（registry.insecure=true，Harbor 无 TLS）
                      └─ 缓存导入/导出：demo/cache:demo-app（跨构建复用层）
```

### 2. buildkitd 常驻部署（`buildkitd.yaml`，kubectl apply 即可）

| 项 | 值 | 原因 |
|---|---|---|
| image | `moby/buildkit:v0.33.0-rootless`（UID 1000） | rootless 三要素之一 |
| `--addr tcp://0.0.0.0:1234` | Service `buildkitd:1234`（ns jenkins） | agent pod 远程连 |
| `--oci-worker-no-process-sandbox` | + `seccompProfile: Unconfined` | rootless 三要素之二/三 |
| AppArmor 注解 `unconfined` | pod template annotation | containerd 2.x 默认 profile 禁 mount → rootlesskit 起不来（最大坑，见 §4） |
| initContainer `chown -R 1000:1000 /cache` | local-path PVC 目录 root 属主 | rootless(1000) 写不了 |
| buildkitd.toml `[registry."harbor…:32037"] http=true` | ConfigMap | daemon 拉取走明文（Harbor 无 TLS） |
| 挂 `harbor-push-config` → /home/user/.docker | （保险，见 §3） | rootless 镜像 HOME=/home/user |
| nodeSelector devops-w1 | local PV 绑节点 | 与 Harbor 同机 |
| readinessProbe `buildctl … debug workers` | — | 探活真实有效 |
| 内核 6.8 | rootless overlayfs 原生可用 | 无需 fuse |

### 3. 最关键的坑：BuildKit 认证走 gRPC session，凭据在 **buildctl 客户端侧**

症状：buildkitd 已挂 `/home/user/.docker/config.json`，构建仍 `401 unauthorized`（build #2 实录）。
原理：buildctl 连 buildkitd 时在 gRPC session 上挂 auth provider，把**客户端自己** `~/.docker/config.json` 里的凭据按需喂给 daemon——拉 FROM、push 输出全算。daemon 本地挂的 config.json 对远程 session 构建不生效。
修法：Secret `harbor-push-config` 再挂一份到 **agent pod 模版的 buildctl 容器** `/home/user/.docker`。
验证手法：先 exec 进 buildkitd pod 用本地 buildctl（tcp://127.0.0.1:1234）跑通拉+推，即可证明 daemon 侧无问题，锁死客户端侧。

### 4. rootless / 构建排障速查（全踩过）

| 症状 | 原因 → 修法 |
|---|---|
| rootlesskit `failed to share mount point /: permission denied` | containerd 2.x 默认给容器套 AppArmor(cri-containerd.apparmor.d) 禁 mount → pod 注解 `container.apparmor.security.beta.kubernetes.io/buildkitd: unconfined` |
| PVC 写不进（permission denied） | local-path 目录 root 属主 → initContainer `chown -R 1000:1000` |
| buildctl 报 401 unauthorized | 见 §3：把 secret 挂到 agent 的 buildctl 容器 |
| push 报 https/TLS 错误 | buildkitd.toml `[registry] http=true` 只管 daemon 拉取；push 明文要在 buildctl `--output` 加 `registry.insecure=true` |
| FROM docker.io 超时 | 香港网络不稳 → `skopeo copy docker://busybox:1.36 docker://harbor…/demo/busybox:1.36` 转存，Dockerfile FROM 改指 Harbor |
| SecretVolume 挂出来路径/名字不对 | kubernetes 插件 SecretVolume 构造参数是 **(mountPath, secretName)**，极易传反——挂完用 Groovy `getVolumes().toString()` 验一遍 |

### 5. agent pod 模版（已配到 cloud `kubernetes`，Groovy 实录）

Jenkins 无 UI 命令行时可走 `POST /scriptText`（crumb 与会话绑定：`curl -c cj.txt` 取 crumb，后续 `-b cj.txt` 带上）：

```groovy
import jenkins.model.Jenkins
import org.csanchez.jenkins.plugins.kubernetes.*
import org.csanchez.jenkins.plugins.kubernetes.volumes.SecretVolume

def j = Jenkins.get()
def cloud = j.clouds.find { it.name == 'kubernetes' }
cloud.getTemplates().removeAll { it.getName() == 'buildkit' }
def c = new ContainerTemplate('buildctl', 'moby/buildkit:v0.33.0-rootless')
c.setCommand('sleep'); c.setArgs('9999999'); c.setTtyEnabled(true)
c.setWorkingDir('/home/jenkins/agent')          // 容器级有 setWorkingDir；PodTemplate 级没有
def t = new PodTemplate()
t.setName('buildkit'); t.setLabel('buildkit'); t.setNamespace('jenkins')
t.setContainers([c])
t.setVolumes([new SecretVolume('/home/user/.docker', 'harbor-push-config')])  // 注意参数顺序！
cloud.addTemplate(t)
cloud.setDefaultsProviderTemplate(null)          // 清掉悬空引用（原值 test）
j.save()
```

### 6. Jenkinsfile（GitLab demo-app 实际版本，构建段）

```groovy
pipeline {
  agent { label 'buildkit' }
  options { disableConcurrentBuilds() }   // timestamper 插件未装，不能用 timestamps()
  environment {
    HARBOR   = 'harbor.devops.local:32037'
    PROJECT  = 'demo'
    APP      = 'demo-app'
    BUILDKIT = 'tcp://buildkitd.jenkins.svc.cluster.local:1234'
  }
  stages {
    stage('Build & Push (BuildKit)') {
      steps {
        container('buildctl') {
          sh '''
            buildctl --addr "$BUILDKIT" build \\
              --frontend dockerfile.v0 \\
              --local context="$WORKSPACE" \\
              --local dockerfile="$WORKSPACE" \\
              --output "type=image,name=$HARBOR/$PROJECT/$APP:b$BUILD_NUMBER,push=true,registry.insecure=true" \\
              --export-cache "type=registry,ref=$HARBOR/$PROJECT/cache:$APP" \\
              --import-cache "type=registry,ref=$HARBOR/$PROJECT/cache:$APP"
          '''
        }
      }
    }
  }
}
```

要点：agent 的 workspace 是 emptyDir，jnlp checkout 后 buildctl 容器同 pod 共享（`--local context=$WORKSPACE` 免二次 clone，优于 kaniko 的 `--context=git://`）；导出/导入缓存指向 `demo/cache:demo-app`，层跨构建复用。

Dockerfile 也已改（FROM 走 Harbor 转存镜像）：

```dockerfile
FROM harbor.devops.local:32037/demo/busybox:1.36
COPY index.html /www/index.html
EXPOSE 8080
CMD ["httpd","-f","-p","8080","-h","/www"]
```
